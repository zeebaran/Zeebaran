# Zeebaran independent production audit

14 November 2026 · Code and configuration review, isolated production builds, browser tests and read-only service checks.

## Assessment

**Weighted engineering score: 8.08/10. Production readiness: 7.5/10.** The public site and editorial workflows have a sound foundation for the current catalog size. Release confidence is limited by untested recovery, live admin latency, and browser coverage that depends on separately provisioned fixtures. No critical issue was confirmed in this review. One high-severity catalog authorization defect and one medium-severity duplicate enquiry defect were fixed and exercised against an isolated build. The current checkout contains both fixes.

For the immediate Firestore question, editing every page does **not** require a database redesign. A successful changed save or publish updates three documents atomically: the page, its revision and the audit entry. Saving then publishing all 14 editorial records would therefore make **84 core document writes** across 28 changed operations. Publishing each once would make **42**. This excludes revision pruning, transaction retries, media uploads and subsequent public cache fills. Typing and editing the preview do not write to Firestore. The practical cost concern is repeated public cache misses or background refreshes under load, followed by media maintenance as the catalog grows.

## Scope and evidence

The initial inventory covered 355 source and test files across the app, components, features, libraries, scripts and tests, with 25 page route files and 18 API route files. Review included marketing and editorial routes, catalog list/detail/search/compare, navigation, forms, media delivery and deletion, auth, Firestore access, configuration, SEO, accessibility, the assistant, podcast and CI. The inventory is a scope count. Deep verification concentrated on the boundaries and workflows below.

- Runtime used a separate production build, an isolated Firebase project with local Auth and Firestore emulators, and a copy of published catalog and CMS content. Credentials and live drafts were excluded from the test copy. The test database and its metadata were disposable.
- The live checks read public CMS and catalog records, index and rule metadata, a configured administrator account, and Cloudinary service availability. No live publishes, deletes, real messages, billing changes, permission changes, or infrastructure changes were made.
- Dependencies were already installed. The review did not install dependencies or replace versions. The local npm advisory query reported zero advisories at the time of the query. It is a point-in-time result.
- A source/config scan across 376 files found zero exact matches for the active Firebase private key and Cloudinary secret. Local environment permissions were restricted and no active environment file was tracked. The check did not scan full Git history, external logs, or deployment artifacts.

## Architecture and data integrity

| Boundary         | Current implementation and evidence                                                                                                                                                                                                                                                                                          |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public rendering | Next.js App Router renders shared page components and CMS overrides. Marketing content uses cached published snapshots. Catalog search and pagination use server-side data with a local fast path for small complete collections.                                                                                            |
| CMS              | `cmsPages/{page}` groups draft and published snapshots by page. Its history subcollection contains revision bodies. `cmsAudit` records changes. Saving compares expected revisions in a transaction. Identical saves and already published identical content short-circuit without core writes. History is loaded on demand. |
| Catalog          | `catalogEntries` holds editorial state. `catalogPublished` is the public projection. A variety references independent rootstock IDs. Publishing and unpublishing maintain both sides transactionally. Queries are bounded and use cursor pagination.                                                                         |
| Site settings    | Shared contact and footer settings use a separate revisioned record. The website consumes the published values through the server. Footer switches preserve contact values.                                                                                                                                                  |
| Media            | `cmsMedia` registers verified Cloudinary originals. Signed uploads, server verification and transactional reference checks protect publishing and deletion. CDN sizing and automatic format/quality are centralized. Logos, favicons, fonts and Open Graph assets can stay in the project as intended.                       |
| Authentication   | Firebase signs in the user. The server verifies the session cookie with revocation checking, then applies verified email, allowlist or role checks. Origin and CSRF checks protect mutations. Client restrictions complement server authorization.                                                                           |
| Assistant        | The launcher loads the panel on demand. Published catalog knowledge is loaded on demand and answers are computed locally. The interaction flag is embedded at build time. Voice uses browser speech recognition where available.                                                                                             |
| Integrations     | YouTube playback mounts on demand. Web3Forms handles configured message-only contact submissions without a Firestore write. The separate attachment workflow requires its own configuration. OpenStreetMap serves the regional map. No Cloud Functions application was found in the reviewed repository.                     |

Live read-only verification found **eight published varieties, four published rootstocks and six saved page records**, plus configured site settings. Six required composite indexes were in the READY state and matched the repository query shapes. The deployed Firestore rules and repository file have different text, with equivalent deny-all client access. The Admin SDK accesses Firestore from the server and is governed by IAM and application authorization. Browser access to a private draft after session revocation returned 401 in the emulator. The signed preview canvas test returned public markup without the private draft marker.

| Local admin navigation           | In a production build with local emulators and pointer-intent prefetch, 14 workspaces showed their headings 43–72 ms after clicking and had preview ready in 142–215 ms. | Live service calls from this Mac | The first Firestore document read was 1,959 ms and the first Auth account lookup was 1,013 ms. Three subsequent reads were 428, 816 and 555 ms. Subsequent Auth lookups were 451, 401 and 376 ms. A separate first published-catalog query took 2,415 ms for 12 records.                                                                                  |

The lab used a warm local server, fresh browser contexts, and no CPU or network throttling. The live checks measured individual calls from the workstation. They did not measure hosting-to-Firestore round trips, real-user p75 Core Web Vitals, production INP, long-session memory growth or behavior under concurrent production traffic. There is no measured before/after speed claim for the two application fixes.

The measured difference supports investigating network and deployment location before changing React rendering or weakening session checks. Firestore is in `nam5`. The deployed compute location was outside the verified scope. Measure the same admin read and mutation paths from the hosting region, including auth, database and response phases. Firebase recommends locating compute near the database to reduce latency. [Firestore best practices](https://firebase.google.com/docs/firestore/best-practices)

- **Normal editorial traffic.** A changed action reads the page and checks each distinct selected media registration as required. It makes the three core writes described above. An unchanged action can still incur those reads. Revision cleanup preserves recent history and publication snapshots and deletes up to 25 rows per pass. Audit collections have a separate retention requirement. [CMS write path](/Users/naveedbhat/Zeebaran/features/cms/server/store.ts:400) · [Revision cleanup](/Users/naveedbhat/Zeebaran/features/cms/server/history.ts:7)
- **Public traffic.** Published CMS reads use a 60-second cache and catalog reads use a 300-second cache, with targeted invalidation. No Firestore real-time listeners were identified in the reviewed application. Small catalogs reuse the cached lists for filtering. Catalog requests with unique search and cursor parameters can create cache misses. Actual billable reads depend on cache sharing, query shape, index-entry rules and traffic. [CMS reader](/Users/naveedbhat/Zeebaran/features/cms/server/public.tsx:13) · [Catalog reader](/Users/naveedbhat/Zeebaran/features/catalog/server/public.ts:51)
- **Free tier.** Firebase lists 1 GiB storage, 50,000 document reads, 20,000 writes and 20,000 deletes per day for an eligible database, and 10 GiB monthly outbound transfer. Daily quotas reset around Pacific midnight. Backups, restores and PITR require billing. The reviewed setup can handle an editorial refresh within those write quotas in isolation. Actual quota headroom requires the production usage dashboard. [Firestore quotas](https://firebase.google.com/docs/firestore/quotas)

## Verification and limitations

- The follow-up for GitHub Actions run 43500480613 corrected the rootstock test’s no-Firebase expectation, the Home tab test’s treatment of router prefetches, and WebKit motion tests waiting for a stationary launcher. The CI-style run passed all 94 applicable Chromium and WebKit cases, with 88 environment-gated skips in those browsers. Both browsers also passed the rootstock deep-link test with a seeded Firestore emulator. Local Firefox failed before test execution because its temporary profile could not be opened. A new GitHub Actions run is needed to confirm the Linux result.
- Baseline lint, type checks and 242 unit tests passed. The audit build passed with 245 unit tests after the new restore regression. The isolated production build also passed with the manually enabled assistant flag. The no-Firebase CI reproduction used a production webpack build locally.
- An emulator-backed public run passed 131 cases in Chromium and WebKit, with four intentional skips and three initial failures. The two podcast failures expected titles from a different fixture set. The contact regression initially drove an invalid submission with a synthetic click that did not focus WebKit's invalid field. After changing it to a normal pointer action, the contact regression passed six repetitions across the two engines. The original mixed result is retained as evidence.
- The first admin emulator run passed 19 cases, skipped six provider-dependent tests and failed five. One failure targeted an old alert locator, two selected a collapsed podcast card after newest-first ordering, and two encountered absent demo media registrations. Correcting those conditions is necessary before treating the admin suite as green. Cloudinary's real destructive operations were outside this review.
- Public responsive checks covered the principal routes and selected detail routes across 320–1920 px. Additional checks covered podcast, comparison, four rootstock details and eight representative admin surfaces. Those added checks found no horizontal overflow. They do not substitute for physical-device, screen-reader or real-user measurements.
- The live identity and database checks do not cover a new Google sign-in, production IAM inventory, deployed headers, an actual Web3Forms email, remote provider write operations, disaster recovery, or production hosting load. The final readiness score accounts for those limits.
