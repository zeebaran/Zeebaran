# Fresh production readiness review

11 November 2026 · Zeebaran · Next.js 16.4.5 / React 19.3.1 / Node 22.23.4

## Verdict

**Weighted engineering score: 8.27/10. Architecture: 8.4/10. Production readiness: 7.6/10.** The application has a sound professional foundation and the important tested workflows work. Six newly verified defects or inefficiencies were fixed with changes to four production files. Public styling, sketches, motion, typography, colors and manually authored content were preserved.

Release readiness remains conditional. The exact requested green fails text contrast, live database deletion protection and point-in-time recovery are disabled, and deployed latency, recovery drills, monitoring and representative traffic have not been proven. This assessment cannot certify every possible state, zero vulnerabilities, zero lag or unlimited free-tier capacity.

This is a fresh review following [the earlier broad audit](production-engineering-audit.md) and [the admin performance investigation](admin-performance-investigation.md). Earlier fixes and measurements remain historical evidence; they are not counted as new improvements below.

## Scope, method and preservation

- Stage 1 captured the existing dirty Git tree and a 275-file, 2,788,044-byte source/configuration/documentation/asset inventory. Private environment values, dependencies, builds, logs and `.local` evidence were excluded. Baseline lint, types, formatting and 110 unit tests passed. Source, route, API, dependency and database inspections preceded the R1–R5 reproductions. R6 received its own live read-only equivalence check before modification.
- Stage 2 applied only the registered, reproducible fixes, then ran the production build, focused regressions, public browser tests, real local admin workflows, live read-only database checks and controlled performance sampling. Details and regression risks are in [the issue register](readiness-issue-register.md).
- No dependency installation/update, Git reset/staging/commit, deployment, provider reconfiguration, live Firestore mutation, schema/index migration or asset cleanup was performed. A temporary signed Cloudinary QA upload was exercised and removed by the test's cleanup. Temporary catalog/CMS writes were confined to guarded demo emulators.
- The user development server on port 3000 and pre-existing emulators were preserved. Separate audit production servers used ports 3375 and 3380. Generated Next.js type declarations were regenerated by verification commands; they are not a design/source change.
- Original photographs/backups, intentionally local OG/brand/icons/fonts, the user's Mission card numbering and all existing page layouts were retained. No speculative dead-code or package deletion was made.

## Architecture and data flow

The App Router serves public pages through Server Components and bounded cached server data. Interactive catalogs, comparisons, forms, maps, motion and the visual editor use client boundaries. Feature modules group catalog, CMS, admin, contact and media code; route handlers delegate validation, permissions and persistence to server modules. This is maintainable for the current application size. Some large editor modules would benefit from careful future extraction when changed for a concrete feature; size alone did not justify a refactor during this review.

Firebase Authentication establishes HttpOnly server sessions. Private admin pages and API operations verify identity, revocation and administrative roles. CMS draft records are separate from published overrides; catalog drafts are separate from public projections. Publishing validates content and relationships, uses revision transactions and invalidates relevant public caches. Comparison options and specifications come from the published catalog and support new entries without new comparison code.

The visual-editor canvas is an intentional security boundary: it verifies the signed cookie and renders public layout markup; it receives the private draft through the authenticated parent editor's checked handshake. It does not independently read drafts. Revoked sessions cannot retrieve or mutate drafts. A regression also supplies draft-preview cookies and proves the canvas contains no private marker. The public-only canvas shell can render for a revoked but otherwise valid signed cookie; that behavior grants no editing capability.

### Read/write efficiency

Queries are bounded and use cursors rather than offsets. Public CMS overrides use a 60-second cache, catalog data a 300-second cache and sitemap catalog data a 3,600-second cache, with publish invalidation. No Firestore `onSnapshot` listener was found in the application paths inspected. Concurrent private GETs are deduplicated while in flight, isolated across session changes and evicted when settled; resolved private data is not retained in a global cross-user cache.

A page containing many editable fields does **not** generate one document read per field. Cost depends on document/query reads, writes, indexes, cache misses and traffic. Current history projection reduces fetched bytes, not billable document reads. Cache reuse across production instances and exact real-user Firebase read volume were not measured. Media search currently searches loaded pages; its corrected empty state makes this limitation explicit. Full-library indexed search remains future functionality if required.

## Security, dependencies and reliability

Verified controls include same-origin and timing-safe CSRF validation, HttpOnly session cookies, verified identity, server roles, revoked-session rejection on private operations, bounded request bodies/cursors, trusted schemas and registered Cloudinary ownership/type validation. Editors can save drafts but cannot publish or delete. Revision conflicts reject stale writes. Published and draft rootstock relationships both protect referenced roots, including a concurrent deletion/link-creation race. Editable text is React-escaped; JSON-LD escapes `<`. No exploitable XSS was reproduced.

Ten direct client read/write attempts were denied by the deployed-rule equivalent in the rules emulator. Admin SDK bypasses Firestore rules, so application server permissions remain essential. Thirteen demo-only rate-limit checks passed, including concurrency, expiry rollover, cross-project isolation and bounded leased cleanup. The public-only canvas boundary is covered separately above.

The production client scan examined **83 JS/map files** and found none of the known configured privileged credential values. Public Firebase app settings, Cloudinary cloud name and Web3Forms public form key are expected public configuration. `npm audit` returned **zero known vulnerabilities** and the installed dependency tree had no errors at assessment time. Every production package had source references; that alone does not establish that every transitive dependency is essential or safe. No dependency was blindly upgraded or removed.

The CSP still permits inline script execution for the existing rendering configuration. This is a defense-in-depth concern, not a reproduced injection exploit. A compatible nonce/hash policy needs deployment/cache verification before adoption. Organization-wide IAM, MFA enforcement, production TLS/edge controls, credential rotation and incident response were not independently certified.

The live database reports **deletion protection disabled and PITR disabled**. Recovery guarantees and scheduled backup restoration were not demonstrated. No paid feature, region migration or account policy was enabled automatically. Error boundaries, service errors, counters and cleanup exist; deployed error aggregation/alert delivery and retention need operational acceptance.

## Media, UI, accessibility and SEO

Actual photographic content uses the existing Cloudinary registry/delivery components and registered Firestore metadata. Responsive transformations, automatic quality/format, intended cropping, lazy loading, dimensions and code-native error/missing placeholders remain intact. The local-only originals picker uses registered metadata rather than restoring deleted public photograph dependencies.

The existing category hierarchy is retained: `banners/{home,varieties,mission}`, `apple-varieties`, `rootstocks`, `orchards`, `orchards/nurseries`, `laboratory`, `products/infrastructure`, `galleries/{home,field-work}`, `partners`, `videos`, `videos/posters`. No public IDs were renamed or remote libraries reorganized during this audit. Local OG, brand/favicon/application icons, WOFF2 fonts and SVG/CSS sketches are intentional. YouTube previews and OpenStreetMap tiles are external provider infrastructure. Legacy-path strings are migration identifiers/redirects where retained.

The fresh matrix covered 26 public routes in Chromium and WebKit at 320, 390, 768, 1024, 1440, 1920 and 2560 pixels: **52 route/engine checks, 364 viewport cases**. Every route returned 200. No document overflow or browser exception was recorded. All 202 visible non-map image instances checked completed with nonzero natural width. Intentional scrolling comparison tables, marquee duplicates, SVGs and map internals were excluded from element-overflow heuristics. Representative screenshots were inspected; this is not exhaustive perceptual validation of every animation frame or device.

Chromium Axe audits found **183 color-contrast nodes across 10 routes** and no other reported violation types in that matrix. WebKit did not run an independent Axe scan. The requested `#8cc63f` on cream measures about 1.87:1, below AA text thresholds; the owner explicitly chose to preserve it. **The site therefore cannot be described as fully WCAG 2.2 AA compliant.** Automated tests also cannot replace keyboard/screen-reader and physical-device testing.

Canonical URLs, indexable public metadata, product structured data, robots exclusions for `/admin/` and `/api/`, the live catalog sitemap and the local OG image were checked successfully. The admin login is `noindex, nofollow`; the sitemap contained no private routes. Search ranking, rich-result acceptance, external link availability and all deployed headers were not proven by these local checks.
