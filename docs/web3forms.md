# Contact delivery with Web3Forms Free

Set `NEXT_PUBLIC_WEB3FORMS_ACCESS_KEY` in the private `.env.local` file locally and in the deployment’s environment. Restart development if the environment has not reloaded, and rebuild/redeploy for production: Next.js includes `NEXT_PUBLIC_` values at build time. This is a public form identifier, intentionally included in the browser; it is not a privileged API secret. Never use a Firebase or Cloudinary credential here.

Both `/contact` and `/contact/simple` use the existing form layout, schema validation, inline errors and sending/success states. The browser sends curated `FormData` directly to `https://api.web3forms.com/submit`. The email address entered by the visitor is the reply-to; the access key determines the receiving mailbox. Name, email, contact number, place, organisation, reason, preferred contact channel, selected topic, message and a reference are forwarded. Contact number and place are required on both forms. Phone numbers accept 7–15 digits with an optional leading plus and normal spaces/brackets/hyphens. Only HTTP success **and** `success: true` count as delivery confirmation. Failed requests retain the visitor’s fields and provide the existing email-draft fallback. Automatic retries are deliberately avoided because provider acceptance can be uncertain after a connection timeout.

Notification emails use **Zeebaran · Enquiry Desk** as their sender name. The payload’s subject includes the enquiry category and submitter’s name, with line breaks removed. On 10 November 2026, the live form’s free **Minimal** notification template was selected and saved in Web3Forms, along with the same sender name and a static fallback subject, `Zeebaran | New website enquiry`. Reloading its settings confirmed persistence. This replaces the default blue labels with a restrained monochrome layout and separators. Custom HTML/logo styling and changing the introductory paragraph are paid features; no plan upgrade was made. The `email` field continues to provide the submitter’s reply-to address.

The full-width Send message button uses a single hover/focus sweep and a moving progress line only while sending. Confirmed success draws an SVG seal/check, then reveals the thank-you heading and receipt copy. The confirmation retains the previous form height to prevent the surrounding page collapsing, and focus moves to its heading. Reduced-motion users receive the completed static state. These effects use CSS/SVG with no additional animation library or Firebase request. The contact forms also share compact desktop field typography, inset dropdown chevrons, 48px controls and mobile input sizing that preserves the browser’s normal page zoom.

Configured Web3Forms submissions bypass `/api/enquiries`, Firestore enquiry storage/rate-limit writes, and Firebase PDF storage. Existing website CMS/catalog reads are unaffected. There is no new library, external widget, analytics hook or additional form-data logging. The Content Security Policy allows only the Web3Forms API origin for this connection. Existing disabled-until-hydrated behavior prevents a JavaScript-free submission from putting private form data into the URL; a direct email link remains available.

This project uses the **Free** plan. The PDF picker is absent while Web3Forms is configured because provider file attachments require Pro. Send documents separately by email. The legacy Firebase/local inbox backend remains available when the key is unset, preserving the existing implementation and its test workflows. A configured Web3Forms failure does not silently fall back to storing or resending the message through Firebase.

The hidden website honeypot still rejects filled submissions in the client; this is only a minor nuisance barrier, not trusted abuse prevention. Web3Forms performs its own server-side spam checks. Its public access key does not authorize data reads. Domain restrictions and stronger provider CAPTCHA configuration can be added through the provider if needed; none is represented as already configured.

## Verification

Unit tests cover field mapping, input validation, missing/placeholder keys, attachments omitted on Free, malformed/error responses, rate limits, timeouts and network failures. Browser checks intercept the provider request before it leaves the browser, exercise both real contact pages, verify sending/disabled/reset/error states and confirm no enquiry API traffic. They do **not** send emails or establish inbox delivery. Verify the final recipient mailbox with a deliberate real submission after deployment.

The button/confirmation sequence was checked in Chromium and WebKit at desktop/mobile sizes, including confirmation focus, retained card height, reduced motion and resetting the form. Scoped axe scans of both contact forms and confirmation states reported no violations; these are not a complete website accessibility certification. The installed Firefox runner could not create its profile, so Firefox motion behavior remains unverified.
